# 传送带与机械臂物流可行性评估

日期：2026-10-31。状态：设计建议，未实现，未确认新增玩法或平衡数值。

结论：适合做成独立物流模组，IC2 作为首批适配对象。基础闭环可行；稳定支持立体铺设、多人、区块卸载和大量物品，需要按一个新模组投入。最难的是物品守恒与确定的物流规则，其次是铺设体验和规模化性能。

本轮仅检查源码和文档。工作区开始时为 main，干净。基线提交为 2026-10-31 检查时的 `5ac0783e`，提交标题为 `docs: record customization history and agent development workflow`，此处日期是检查日期，不是提交日期。没有构建、运行游戏、测量性能或核验玩家正在使用的 JAR。

从可玩性看，传送带可以让堵塞、缺料和设备闲置变得可见，也能把矿物处理、烧炼和生电收集组织成能看懂的生产线。Minecraft 的高低差适合桥梁、坡道和多层厂房。不过物流本身不会自动增加生产深度。如果现有机器加工需求不高，或已有管道成本很低，传送带可能只承担展示作用。应先用现有配方完成一条实用产线，再判断是否需要新的生产目标；本轮不建议直接修改 IC2 配方或倍率。

建议采用单通道、离散货位的初版，保留空间布局和吞吐规划。双通道会增加近侧、远侧抓取以及侧向汇入规则，适合后续单独评估。[Factorio 的官方 Wiki](https://wiki.factorio.com/Transport_belt) 将速度、密度与吞吐量分开描述；这里借鉴这种区分，不照搬其具体数值。初版建议每货位一个物品，搬运批量和堆叠运输另设升级，避免一个图标有时代表一个物品、有时代表一整组，导致吞吐量难以理解。

| 玩家操作或场景 | 建议行为 |
| --- | --- |
| 直线、转弯、上坡、下坡 | 格点连接，方向清晰，转弯不凭空损失或增加吞吐 |
| T 形汇入 | 空位可用时轮流接受输入，避免某支路长期饿死；总吞吐仍受出口限制 |
| 一路分为两路 | 使用独立分流器，默认轮流分配到可用出口，后续增加优先级和过滤 |
| 两路交叉但不混合 | 初版使用坡道和桥梁；同层交叉需要专用双通道方块，不能和普通交汇自动混为一谈 |
| 下游满载或未连接 | 货物停在带上并逐步回堵，停止上游抓取；默认不抛出掉落物 |
| 目标机器满载 | 机械臂等待，保留明确的物品归属 |
| 红石控制 | 可启停机械臂或带段，便于接入现有生电装置 |
| 生电农场的散落物 | 使用漏斗或专用收集入口接入；单纯支持库存并不等于已支持掉落物收集 |

机械臂必须区分源位置、源访问面、目标位置、目标访问面和过滤条件。反转箭头只决定搬运方向，不能决定目标槽位。原版熔炉通常从上方进原料、侧面进燃料、下方取产物，底部还涉及空桶等特殊规则。实施时须以锁定的 26.3 源码和真实容器测试确认，不能为了从任意侧面操作而绕过容器限制。需要更自由的布局时，可以设计明确的端口适配器，再单独评估其玩法。

最小闭环为煤箱经机械臂、传送带向熔炉燃料侧供煤，另一路向顶部供原料，底部机械臂将产物送到成品箱。第二条闭环接 IC2 打粉、烧炼，再测混合物品和过滤。为避免末端设备长期吃不到料，机械臂还应限制对单台机器的预填充量；具体阈值通过试玩选择，不能仅靠公平汇流解决所有分配问题。

基础运输建议以材料成本和吞吐上限作限制，不强制依赖 IC2 的 EU。这样卸掉 IC2 后仍可使用。高速机械臂可另做可选供电适配，但 EU、FE 的转换比例和成本不能在本轮自行决定。短距离装卸保留漏斗的便利，传送带承担可视化长距离与多分支运输，尽量避免让两套系统完全重复。

当前仓库有可用的接入基础：

- [Ic2Capabilities.java](../mods/ic2/src/main/java/ic2/forge/Ic2Capabilities.java) 注册 `Capabilities.Item.BLOCK`，使用 `ResourceHandler<ItemResource>` 和按面的 `WorldlyContainerWrapper`。
- [TileEntityInventory.java](../mods/ic2/src/main/java/ic2/core/block/tileentity/TileEntityInventory.java) 定义方向与槽位限制，必须保留。
- [TileEntitySortingMachine.java](../mods/ic2/src/main/java/ic2/core/block/machine/tileentity/TileEntitySortingMachine.java) 处理自己的缓冲库存和过滤输出，并不承担主动机械臂抓取。新设备应使用不同名称，不修改现有已确认语义。
- [EnvItemHandlerForge.java](../mods/ic2/src/main/java/ic2/forge/EnvItemHandlerForge.java) 的目标识别仍主要针对原版容器和 IC2 库存，不宜直接作为新通用物流层。
- [ItemRoutingGameTests.java](../mods/ic2/src/main/java/ic2/core/gametest/ItemRoutingGameTests.java) 已有能力查询和事务回滚测试模式，可以借鉴验证方法，不能将历史通过结果当作新模组兼容证明。

新的物流层优先访问目标按面公开的标准能力，没有公开能力的特殊存储再做适配。[NeoForge 传输重构说明](https://neoforged.net/news/21.9-transfer-rework/) 和[事务文档](https://docs.neoforged.net/docs/inventories/transactions/) 说明了资源处理器与提交、回滚机制。访问到的事务文档标注 26.1，不能直接视为 26.3 的 API 保证；本仓库源码已经使用相关类型，完整方法行为仍须以锁定依赖验证。标准接口也不保证所有第三方实现正确。

建议每个物品只存在于一个权威库存中。带上货物用资源、数量和轨道位置记录，客户端绘制移动模型，不为每件货物创建原版掉落实体。服务器负责搬运结果，客户端根据速度和时间插值；变化时同步，进入视野时补快照。这样能减少物理与网络负担，但不能在测量前承诺容纳多少条带或多少件物品。

原型可按方块存储，必须限制每 tick 的移动次数，避免同一物品由于更新顺序在一 tick 内穿过整条带。长直线以后可合并为带段计算，弯道、机械臂和分流器作为交互节点。第一版就记录吞吐、服务器 tick 时间、客户端帧时间、网络流量和存档体积；根据测量决定是否需要更复杂的带段模型。

机械臂动画不必对应一个真实的中途库存。最小实现可以在一次逻辑提交中完成搬运，再播放动画；若希望机械臂真正持有物品，则必须保存手中库存，处理目标消失、断电、卸载和拆除。事务解决一次逻辑更新的回滚，不能单独保证进程崩溃时跨区块磁盘写入原子性。正常保存重启与异常退出要分别设计和验证。

跨区块默认只在两端处于可运行状态时传输，不隐式强制加载区块。末端卸载就停止交接，重新加载后恢复；单纯能查到方块不等于区块正在正常 tick。拆带、爆炸、玩家拿取和机器换向也必须遵守物品只返还一次。过滤模式与保存数据分离，即使允许按物品类型过滤，也不能抹掉名称、耐久、附魔、药水或 IC2 动态数据。

3D 预览是可行的。建议用专用铺设工具，选起点、移动终点，展示格点路线、方向、材料数量和无效段。初版用直线、折线和显式坡道，允许切换先横后纵，支持中途加锚点。Shift 配合滚轮或可重绑的升降键改变目标高度，保留 Minecraft 潜行习惯，并实际检查与 IPN 等现有按键的冲突。

客户端只给预览；确认后服务器重算并检查距离、材料、碰撞、放置权限与可运行区块。首版限制单次长度，在验证失败时整次拒绝，避免静默铺出半条线路。若以后支持分批施工，界面必须明确显示未完成部分。还需实测透视遮挡、透明渲染和整合包客户端效果。自动绕开任意建筑、自由曲线、蓝图批量复制会扩大范围，可以延后。

| 阶段 | 可交付能力 | 通过条件 |
| --- | --- | --- |
| 最小可玩闭环 | 单通道直线和转弯、机械臂、过滤、原版箱子与熔炉、IC2 代表机器；先手动铺设 | 实际产线可运行，满载停机，输入输出和内部库存总量守恒 |
| 完整首版 | 坡道桥梁、汇流分流、红石、受限折线预览、批量放置 | 多人同时操作、拆装、跨区块停运恢复，以及真实保存关闭重启均正确 |
| 扩展 | 速度升级、优先级、配置复制、蓝图与大型网络优化 | 有性能基准与需求证据，再选择双通道、同层交叉和供电联动 |

首个阶段是中等规模原型；第二阶段开始属于较大的新模组开发。排期必须等物品状态模型、目标规模和一次真实客户端原型验证后再估算。优先做熔炉闭环，可以同时检验接入方向、供料公平性、堵塞与可读性。最终值得追求的体验是玩家能看懂为什么停机，并通过调整布局解决问题。
